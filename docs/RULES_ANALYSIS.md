# 赛制研究与本次修订依据

依据：仓库 `docs/任务书.md` 第五章、5.3 自进化类、第六章，以及 `/tmp/selfEvolutionTask/1-fixed-step` 的六份题面、API 文档和三个部署规范。
用户本轮写的 `/tmp/selfEvolution/1-fixed-step` 在本机不存在；实际样本位于上述 `/tmp/selfEvolutionTask` 路径。

## 任务书明确的规则

1. 自进化任务由开拓者前往两个任务点领取，通过独立终端沙盒执行基础 shell/Python，再提交答案。沙盒不能访问外部网络。
2. 5.3 使用“查询北京天气 → 上海天气 → 广州天气”的例子，明确要求根据任务 1 的探索形成固定 SOP 或 SKILL，以快速完成后续任务。
3. 每个任务点的任务总数有上限。完成、超时、离开任务点周围一格、开拓者死亡均使任务结束；同点再次领取需等待 30 回合。
4. 第六章完整完成奖励为 `任务积分奖励 + 5 × 任务标准回合数 / (实际完成回合 - 接取回合)`；标准回合数等于超时回合数。因此完成正确只是基础，缩短交互链路有直接得分价值。
5. 部分完成按通过率计算奖励；题目结束不论是否全部完成，均消失并按规则结算。

这些条款支持“同类实例复用学习”的设计，并不证明官方只有两类题或每类固定三题。两个任务点不等于全球类型清单只有两个。

## 原始出题方式的证据

- API 任务 1：北京文化遗产查询；提供文档入口，文档实际存在鉴权、地区参数等偏差，需要探索真实接口。
- API 任务 2：南京，题面明确“同一服务、同一认证、同一参数格式”，只更换城市。
- API 任务 3：成都，再次明确 API 不变，只更换城市。
- 部署任务 1：alpha；读 spec，修复目录、指定配置与脚本权限，再运行 check 获取 token，并提示整理 SOP。
- 部署任务 2/3：beta/gamma；工作区、端口、服务名和 token 改变，目录/配置/权限这套故障与验收流程保持一致；题面提示复用 SOP 或脚本。
- 原始 manifest 的顺序是部署1、API1、API2、部署2、API3、部署3。这说明经验应按类型保留，不能要求同一类型三题必须连续出现。

## 上一版的问题

上一版将不同认证、分页、字段、故障与验收方式做成 34 道独立题。它能检查单题适应能力，但没有提供每种机制对应的后续同类实例，也未保证服务地址、沙盒文件和经验状态在任务间持续存在，因此不足以评估题目要求的自进化过程。

## 本次对应修订

- **横向构造类型**：不同主题/协议或部署格式对应不同题组。
- **纵向固定机制**：每组 1、2、3 只有已说明的业务参数和正确答案变化，不把认证突变或新故障放入后两题。
- **保留学习成果**：同组 API 服务只启动一次；沙盒、旧工作区、技能目录、Agent experience 持续存在到整组实验结束。
- **减少无关重学**：后续题明确说明沿用首题机制，仍保留查阅规范的入口；不会将参考 SOP 预置给真实模型。
- **测量而非假设提速**：报告正确性、解题回合、LLM/工具/HTTP 调用、错误提交以及学习产物；不把参考程序的速度称为模型自进化效果。
- **测试跨类型记忆**：提供两组交错运行，共用 Agent 状态，并按类型分别维护 30 回合冷却。

本轮范围是题目与离线解题实验环境。任务点寻路、接取、死亡、离点、昼夜调度、完整金币积分结算仍属于完整对局模拟范围，没有在本轮声称实现。
